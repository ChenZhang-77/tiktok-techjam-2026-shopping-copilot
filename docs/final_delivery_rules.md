## 产品与运行

1. **交付 Headless Agent。** 对接官方 Python 评测接口，不新增真人聊天网站、账号系统、HTTP 后端部署、多用户服务或工业向量数据库；现有可视化仅用于演示和诊断。“不部署后端服务”不等于“不实现 Agent 后端逻辑”。

2. **一个提交包，两套配置。** 离线和 LLM 增强共享同一 Agent 入口及控制逻辑，不要求评委切 Git 分支拼接运行。独立包是我们的交付组织方式，文件名和打包格式服从最终官方要求。

3. **离线不等于无模型。** 离线配置保留准备好的本地 catalog、MiniLM/向量资产及已保留的条件式检索；安装准备阶段可按说明下载，正式运行不自动下载模型、不调用外部 API。

4. **默认离线，增强只显式开启。** 在运行前选择配置；不做会话中途热切换，不因机器存在密钥或网络而自动启用 LLM。增强启用后仍按原有回合资格门控，不是每一轮都调用模型。

5. **LLM 只迁入已验证的 F2 商品重排。** 只对合格 Browsing 请求的已有 Top-10（受 top_k 限制）进行约束保护的重排，保持该轮集合成员；不更换模型、prompt、温度、门控、约束保护或其他冻结参数来偷偷调优，不把“重排”宣传成“更强对话理解”。

6. **保留多轮能力与契约。** 保留 Buying/Browsing、信息累积、意图覆盖、拒绝和无偏好处理、查询蒸馏及澄清。收尾允许修复合约、接线、打包和可复现性缺陷，但不能将算法策略重写混在整合中；行为变化须单独说明并验证。

7. **冻结未完成实验并披露覆盖限制。** 不重启 A13、A14、profile、B11、B12 或模型搜索。按 PDF 四大支柱逐项标记已实现、条件启用和未覆盖，例如长期画像、澄清策略与条件式 dense 的限制；披露不是“完全满足要求”的替代品。若最新官方明确某个缺口为资格硬门槛，须报告并调整范围，不能靠改宣传通过。

## 故障、成本与安全

8. **LLM 故障不打断可用的离线链路。** 缺密钥或网络不可用时继续离线；超时、非法返回或预算耗尽时保留本轮重排前的顺序。必要 catalog 缺失等基础错误必须单独报出，不能伪装成正常降级。

9. **如实标注实际执行。** 记录请求配置、实际执行路由、调用/成功/回退次数与原因。正常门控跳过不是故障，开启了配置不等于成功使用 LLM；全程未成功调用不能算增强验证通过。缺本地 dense 资产的结构化降级也不能冒充完整 B9 复现。

10. **调用有界，不自动扩大费用。** 封装沿用 F2 的 8 秒请求超时、无自动重试、连续三次错误或认证错误停止进一步 LLM 调用的原则，之后继续本地服务；同时设置请求数、费用和总时长上限。8 秒不是官方时限承诺，须核对整轮耗时与官方限制；若不适配则重新验证或用离线参赛，不静默改参数。新付费验证须另行明确授权和预算，旧实验预算不是当前授权。

11. **最小外传，密钥隔离。** 只有显式增强且获得相应调用授权后，才按原 F2 配方发送有界蒸馏查询、当前约束和别名化商品文本。不给 LLM 发送 profile、目标 ASIN、标签、未来轮次或评测信息；密钥不进代码、Git、日志、视频或提交包。普通测试和打包不得触发真实调用。

12. **官方数据与接口不变。** 保持 reset/respond 和合法返回结构、会话隔离、每会话最多 10 轮、真实且唯一的 Top-10 catalog ASIN。50k catalog 只读；不改 evaluator、标签或评分公式，不向运行时提供目标商品/场景标签/未来信息，不写样本专用答案。

## 分支融合与验收

13. **在独立收尾分支做定向迁入，main 是唯一对外提交入口。** 当前基线为 `release/track4-final-integration@3b01416`（已获取的 main 可视化更新及 Chen 默认运行时）；从 `llm@a9e34ae` 提取准确 F2 依赖和测试，从 P0 借鉴打包工具后重建。验收后再按授权合入/推送 main，Devpost 只链接最终 main 并记录 commit；其他 GitHub 分支保留，不要求评委运行其他分支。同一公开仓库中的其他分支并不会因此隐藏。不要整枝合并全部历史实验，不恢复旧 P0 运行时，不覆盖队友修改；实施前重新检查工作区与来源差异。

14. **可视化只做必要纠错。** 展示真实运行的多轮轨迹、推荐变化、配置、调用/回退及结果；修复错误模式映射和旧成绩错配。严格区分 Agent 可见数据与 evaluator 的目标/排名/命中信息，结果绑定源码、配置、数据和模型版本；录制回放与实时执行明确标注。

15. **离线集成以行为一致为门槛。** 先运行测试，再用固定 Development-160 和四折验证新入口与选定来源的响应、推荐、问题及执行路径一致（排除明确允许的计时和展示诊断差异）。不能只对齐一个四舍五入总分；出现差异先诊断，不边改策略边解释成绩。

16. **增强以新包实测为门槛。** 先通过无调用的 baseline/placebo 和故障测试，获得新授权后再做两轮独立真实请求，沿用原 F2 的质量、四折、配对和可靠性门槛。TechnicalScore/MRR 收益不能以 HR/MTTC 或硬约束损失换取；必须记录延迟长尾、成本和降级。Mock、历史分支结果和一轮偶然提升不能替代新包验证；不通过就不作为正式增强参赛配置。

17. **必须独立启动。** 从干净目录按文档准备数据/依赖后，不能依赖本机绝对路径、兄弟工作树软链接或开发者私有缓存。分别检查正常本地资产、缺失/损坏的可选资产、无密钥、无网络、超时、非法返回和预算耗尽；区分“可运行的降级”与“复现声明的完整模型配置”，记录初始化、内存和实际运行环境。

18. **正式评分配置与软件默认分开。** 软件默认仍离线；若主办方明确允许外部服务和凭据，并且新包增强复验及资源限制均通过，优先选择增强争取成绩，否则使用已验证的离线配置。最终固定一个明确参赛配置，不让评委猜；本轮不假定网络/密钥/模型资格已获许可。

19. **证据不混用、不夸大。** 只用固定 Development-160 和四折进行开发选择，不在 Full-200 或已暴露 holdout 上调优。按用户后续询问，计划在最终配置冻结后安排一次 Full-200 公开报告关卡（不是现在开始迭代运行）；保存总分、逐会话结果、配置和源码/数据哈希于 main 的评测材料，不把标签放入 Agent 运行包。Full-200 明确标记为完整公开集、非未见验证，不与 Development-160 直接作效果增量比较；增强 Full-200 另需付费授权。报告包含 HR、MRR、MTTC、TechnicalScore、折/场景差异、成本、延迟及资源信息；旧结果标历史、新包结果有源码/配置/输入哈希。TechnicalScore 不是比赛总分，800 私有会话表现未知，不声称预知泛化或获奖效果。

## 提交材料与完成边界

20. **交付材料齐全且真实。** 交付 Agent/必要模块、依赖与环境说明、复现命令、方法和模型报告、成本/延迟/限制、数据与模型来源/许可证、团队贡献、README、Devpost 文案及视频。对外文案默认英文，内部协作用中文；贡献依据实际工作和证据填写，不能仅靠提交数分配，也不能虚构。公共材料和最小运行包分开，数据/权重依规则和许可分发，不把私密实验材料打包出去。

21. **演示突出端到端与可解释证据。** 默认覆盖 Buying、Browsing、意图覆盖、无偏好和一次可控 LLM 降级；用短视频展示可运行过程及有明确来源的离线/增强对比，不为视频另造不一致系统。2026-08-31 核对[赛事官网](https://tiktoktechjam2026.devpost.com/)后，按公开 3 分钟 YouTube 演示准备，取代此前约 3–4 分钟的内部建议；截止为 2026-09-01 12:00 SGT，视频也须在此前补齐。无前端的 API/推理/结果分析走查可满足 PDF 的演示形式。

22. **公开材料是提交完成的必要部分。** PDF 要求公开代码仓库、公开 YouTube 视频并在 Devpost 描述中链接，README 包含安装、复现、局限和团队贡献；视频不能使用未获许可的第三方商标或版权内容。保留提交记录和最终材料对应的源码/配置版本，不能把本地打包完成或文案草稿当成实际提交完成。

23. **按验证顺序收尾，测试绿不等于完工。** 顺序为：冻结规则与接口 → 定向融合 → 离线/故障验证 → 授权后的增强复验 → 独立包冷启动 → 证据与文档一致性审核 → 演示录制和提交材料 → 授权后的发布/提交。只有选定参赛配置可复现、无阻塞缺陷、材料齐全且实际提交确认后，才称“比赛提交完成”；付费或公开操作未获授权时，只完成不受影响的本地工作并如实报告剩余事项。

24. **默认接受规则不等于授权外部操作。** 本轮只整理规则和文档，不开始代码整合。后续代码实施以实现任务为准；付费调用/预算、外部数据发送、Git push、修改仓库可见性、上传公开视频、Devpost 最终提交仍需各自明确授权。默认不删分支、不强推、不动用户 stash，不自动重跑旧文档的发布命令。
