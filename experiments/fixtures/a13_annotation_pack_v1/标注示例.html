A13 清晰标注示例

下面不是让你照抄答案，而是说明每个字段什么时候该填、什么时候必须留空。

先判断是否应该 abstain

  1. 先读 current message。新增字段的 evidence 只能来自这里。
  2. 再看 prior state，只用来判断本轮是否明确覆盖旧属性，不要把旧约束复制进 label。
  3. 如果能得到一组完整、无矛盾、可逐字举证的变化，选择“可以标注”。
  4. 如果替换指令缺少新值，或同一个值既被要求又被排除，选择 abstain=true。
  5. 最后检查：每个 value/evidence 是否来自当前消息，hard 是否符合语气。

示例 1｜明确替换：标 override 和新值

Prior state
color=black
Current message
Actually, make it blue instead.

为什么这样标：blue 是本轮明确的新值，instead 表示替换旧颜色，所以同时标 positive color 和 override color。

不要这样标：不要把旧的 black 再写入 rejected；当前消息没有逐字排除 black，状态替换由 override 表达。

{
  "intent_hint": null,
  "positive_constraints": [
    {"attribute":"color","value":"blue","evidence_span":"blue","hard":true}
  ],
  "rejected_constraints": [],
  "no_preference_attributes": [],
  "override_attributes": ["color"],
  "semantic_terms": [],
  "abstain": false
}

示例 2｜无偏好与排除值可以共存

Prior state
无
Current message
Any color is fine, but not black.

为什么这样标：用户没有正向颜色偏好，但仍明确排除 black。无偏好不等于接受所有颜色。

不要这样标：不要创建 color=any，也不要因为“随便”而丢掉 black 的排除条件。

{
  "intent_hint": null,
  "positive_constraints": [],
  "rejected_constraints": [
    {"attribute":"color","value":"black","evidence_span":"black"}
  ],
  "no_preference_attributes": ["color"],
  "override_attributes": [],
  "semantic_terms": [],
  "abstain": false
}

示例 3｜一句话中同时有想要和排除

Prior state
无
Current message
I want a leather bag, but not black.

为什么这样标：I want 支持 buying；leather 是明确材质要求，black 是明确排除颜色，二者不冲突。

不要这样标：不要因为句中有 but 就 abstain；只有同一个 attribute/value 自相矛盾时才必须 abstain。

{
  "intent_hint": "buying",
  "positive_constraints": [
    {"attribute":"material","value":"leather","evidence_span":"leather","hard":true}
  ],
  "rejected_constraints": [
    {"attribute":"color","value":"black","evidence_span":"black"}
  ],
  "no_preference_attributes": [],
  "override_attributes": [],
  "semantic_terms": [],
  "abstain": false
}

示例 4｜弱偏好：hard=false

Prior state
intent=buying
Current message
I would prefer something packable.

为什么这样标：would prefer 是弱偏好，不是不可妥协的要求，因此 feature 使用 hard=false。

不要这样标：不要因为 prior state 是 buying 就复制 intent；这里的 intent_hint 只反映当前消息提供的新意图证据。

{
  "intent_hint": null,
  "positive_constraints": [
    {"attribute":"feature","value":"packable","evidence_span":"packable","hard":false}
  ],
  "rejected_constraints": [],
  "no_preference_attributes": [],
  "override_attributes": [],
  "semantic_terms": [],
  "abstain": false
}

示例 5｜不完整的替换指令：必须 abstain

Prior state
color=black
Current message
Use a different color instead.

为什么这样标：用户想换颜色，但没有给出新颜色，也没有明确表示颜色随便。此时不能安全生成完整 delta。

不要这样标：不要只填 override_attributes=["color"]，也不要猜测任意替代颜色。

{
  "intent_hint": null,
  "positive_constraints": [],
  "rejected_constraints": [],
  "no_preference_attributes": [],
  "override_attributes": [],
  "semantic_terms": [],
  "abstain": true
}

示例 6｜同一个值既要又不要：必须 abstain

Prior state
无
Current message
I want red, but no red.

为什么这样标：同一个 color=red 同时被正向要求和明确排除，没有可靠规则决定哪一半覆盖另一半。

不要这样标：不要同时输出 positive red 和 rejected red，也不要擅自认为后半句一定覆盖前半句。

{
  "intent_hint": null,
  "positive_constraints": [],
  "rejected_constraints": [],
  "no_preference_attributes": [],
  "override_attributes": [],
  "semantic_terms": [],
  "abstain": true
}

示例 7｜evidence_span 与 value 的区别

Prior state
无
Current message
Keep it under 80 dollars.

为什么这样标：value 是小写规范值；evidence_span 是当前消息中的逐字证据。这个例子两者相同，但职责不同。

不要这样标：不要写 value="cheap"，因为原文没有 cheap；也不要只截取 80 而丢掉预算关系。

{
  "intent_hint": null,
  "positive_constraints": [
    {"attribute":"budget","value":"under 80 dollars","evidence_span":"under 80 dollars","hard":true}
  ],
  "rejected_constraints": [],
  "no_preference_attributes": [],
  "override_attributes": [],
  "semantic_terms": [],
  "abstain": false
}

示例 8｜无法安全归入属性时使用 semantic_terms

Prior state
intent=browsing
Current message
Show me something quiet when it moves.

为什么这样标：quiet when it moves 对检索有用，但不适合强行塞进受限的结构化属性值中，因此保留原文短语。

不要这样标：不要把完整短语拆成脱离语境的 quiet，也不要同时把同一短语重复写入 positive constraint。

{
  "intent_hint": "browsing",
  "positive_constraints": [],
  "rejected_constraints": [],
  "no_preference_attributes": [],
  "override_attributes": [],
  "semantic_terms": ["quiet when it moves"],
  "abstain": false
}

示例 9｜明确清除旧偏好：no-preference + override

Prior state
material=cotton
Current message
Any material is fine now.

为什么这样标：当前消息明确把 material 改成无偏好，因此既标 no-preference，也标对旧 material 的 override。

不要这样标：不要创建 material=any；“随便”是状态变化，不是商品属性值。

{
  "intent_hint": null,
  "positive_constraints": [],
  "rejected_constraints": [],
  "no_preference_attributes": ["material"],
  "override_attributes": ["material"],
  "semantic_terms": [],
  "abstain": false
}

字段速查

字段什么时候填常见误区
intent_hint当前消息本身明确支持 buying/browsing照抄 prior intent
positive_constraints当前消息明确想要或接受某个值把 any/fine 当成值
rejected_constraints当前消息明确排除某个值把被覆盖的旧值自动当 rejected
no_preference_attributes当前消息明确表示某属性随便误解为接受全部值、丢弃明确排除
override_attributes明确覆盖 prior 属性，且本轮有新值/排除/no-preference只有“换一个”也强行标 override
semantic_terms有检索价值但无法安全归入属性的原文短语与 positive/rejected 重复
abstain无法得到完整、无矛盾、可举证的 deltaabstain 时仍填写其他 label 字段
